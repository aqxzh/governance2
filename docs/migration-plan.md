# Governance.kz — план локального переноса на SvelteKit

Статус: первый контрольный образец реализован локально; остальные разделы и деплой не завершены. Текущий объём и проверки — в `migration-status.md`.

## Цель и границы

Перенести существующий сайт с React/Figma Make на стек из `unified_stack_spec.md`, сохранив узнаваемый дизайн и работающие пользовательские сценарии. Сначала довести новую версию локально и принять её визуально; сервер и прод не менять.

Основа: TypeScript strict + Svelte 5 + SvelteKit + Vite + adapter-static; Tailwind CSS v4 + shadcn-svelte + Bits UI; Paraglide JS; pnpm, svelte-check, ESLint, Prettier, Vitest, Playwright.

Не добавлять FastAPI, PostgreSQL, AI-рантайм, авторизацию или новую бизнес-логику только ради соответствия справочнику. Они подключаются по реальным функциям продукта.

## Проверенные исходные факты

- React-источник: `089d964` в `main`; локальный SEO-фикс: `b4a339f` в `fix/seo-site-json`.
- Главная, страницы контуров, модалки и переключатель языков находятся в `imports/index.tsx` (3093 строки).
- Старые входы: `/`, `/#diagnostics`, `/#coordination`, `/#simulator`, `/?food=1`. Есть обработчик hashchange; это не полностью безадресная навигация.
- Симулятор содержит пять модулей и раздел LLM-to-LLM, отображаемые последовательно на одной странице. Не превращать их автоматически в шесть новых самостоятельных продуктов.
- `src/mobile/MobileApp.tsx` не импортируется текущим приложением. Не считать его обязательной отдельной страницей без проверки назначения.
- Языковой переключатель меняет выбранную метку, но не переводит контент.
- Форма уже вызывает FormSubmit из `src/lib/sendApplication.ts`. Наличие интеграции подтверждено кодом; активация сервиса и реальная доставка писем не проверены.
- `PRODUCT.md` содержит устаревшие сведения. Сверять каждое утверждение с кодом и браузером, а не переносить документ буквально.
- В текущем сайте есть зарегистрированный service worker: при будущем переключении версии нужно учесть старый кеш.

## 1. Зафиксировать эталон и карту сценариев

1. Сохранить текущую React-версию как эталон в Git. Новую версию делать в отдельной ветке `migration/sveltekit` и соседнем worktree `../website-svelte`, чтобы оригинал оставался доступен для сравнения.
2. Снять полный набор контрольных скриншотов: главная, все контуры, симулятор, FoodFlow, формы и модалки на 390, 768 и 1440 px. При необходимости добавить 320 px для проверки переполнений.
3. Выписать порядок секций, ссылки, интерактивные состояния, тексты, изображения и видео. Проверить все пути к медиа, включая различия `.mov`, `.mp4`, `.webm`.
4. Для визуального разбора использовать SuperPC/glm-5.3-flash и программную проверку DOM/стилей. Выводы vision-модели о предполагаемом поведении подтверждать кодом или действиями в браузере.
5. Отдельно согласовать судьбу FoodFlow, неиспользуемого MobileApp, PDF и фактических показателей. Не придумывать документы, цифры или кейсы.

Результат: список обязательных экранов и сценариев, эталонные изображения, перечень недостающего контента.

## 2. Собрать чистую основу

- Создать SvelteKit-проект в корне нового worktree; существующие React-файлы останутся в исходном worktree и Git, а не в опубликованном приложении.
- Подключить TypeScript strict, Tailwind v4, shadcn-svelte, Paraglide и инструменты проверок.
- Зафиксировать совместимые версии Node.js/pnpm, `packageManager` и единственный `pnpm-lock.yaml`.
- Добавить команды `dev`, `check`, `lint`, `format`, `test`, `test:e2e`, `build`, `preview`.
- Обновить AGENTS.md под реальный проект; убрать зависимости от Figma Make-плагинов и автогенерации.
- Настроить adapter-static с предрендерингом публичных страниц и гидратацией интерактивных элементов. Не отключать SSR глобально: иначе HTML будет пустой оболочкой.
- Это осознанный SSG-вариант вместо базового SPA из справочника: SEO-лендинг получает готовый HTML при сборке, постоянный Node.js на сервере не нужен. Согласовать этот выбор до реализации.

Результат: пустой проект собирается в статические файлы, проверки запускаются.

## 3. Настроить дизайн через shadcn-svelte и Tailwind

Сохраняем: белый фон, основной акцент `#2242D6`, тёмный текст `#0D0F16`, контейнер до 1170 px, тонкие разделители, нумерованные надзаголовки, преимущественно плоский дизайн. Симулятор сохраняет отдельное тёмное оформление.

- Настроить semantic tokens shadcn: primary, foreground, background, muted, border, ring, radius. Не оставлять стандартную тему shadcn вместо бренда и не размножать hex-значения по компонентам.
- Самостоятельно разместить IBM Plex Sans/Mono и используемый Inter, проверить лицензии и наличие казахских символов. Приоритет — убрать зависимости шрифтов от `static.figma.com`.
- Определить типографическую шкалу, отступы, радиусы и адаптивные варианты через Tailwind/CSS-переменные.
- Взять готовые Button, Card, Dialog, Tabs, Table, Sheet, Input, Label, Textarea и необходимые дополнительные компоненты из shadcn-svelte. Не переписывать управление фокусом, клавиатурой, закрытием модалок и табами вручную.
- Table использовать для простого реестра; TanStack Table не нужен без сортировки/фильтров.
- Писать только прикладные композиции: секции лендинга, надзаголовки, карточки решений, схема процесса, иллюстрации и слайды. Не добавлять обёртки над каждым компонентом без необходимости.
- Мобильную навигацию сделать через Sheet; убрать переполнения и слишком крупный hero-текст, сохранить смысл и визуальный характер.

Результат: шапка, hero и несколько эталонных компонентов выглядят узнаваемо на десктопе и телефоне.

## 4. Встроить локализацию сразу

- Использовать `@inlang/paraglide-js` по техспеку.
- Локали: `ru`, `kk`, `en`. Кнопки интерфейса: RU, KZ, EN. Казахский код языка — `kk`, не `kz`.
- Рекомендуемая URL-схема: `/ru/`, `/kk/`, `/en/` и локализованные дочерние страницы; `/` остаётся совместимым русским входом. Основные индексируемые адреса имеют однозначную локаль.
- На раннем этапе проверить Paraglide + локализованные URL + предрендеринг на одной тестовой странице: каждая локаль должна дать отдельный корректный HTML. Не полагаться на cookie при построении статических страниц.
- Вынести тексты в `messages/ru.json`, `messages/kk.json`, `messages/en.json`; использовать генерируемые типизированные функции сообщений, а не собственный i18n-слой.
- Переключатель сохраняет текущую страницу. Перевести также aria-label, alt, ошибки, статусы отправки, подписи таблиц, title/description.
- Использовать Intl для чисел и дат. Проверять полноту ключей и параметров сообщений автоматическими тестами.
- Русский контент — источник. Переводы kk/en проходят редакторскую проверку; черновой машинный перевод не выдавать за утверждённый.
- Тексты внутри PNG и видео учитывать отдельно: замена языка интерфейса не переводит изображения автоматически. Для ключевых схем нужны локализованные версии либо перенос подписей в HTML/SVG.

Результат: язык реально меняет весь переносимый интерфейс, сохраняется при переходах, корректно указан в HTML.

## 5. Перенести страницы и сценарии по очереди

Порядок: главная → диагностика/координация → симулятор → FoodFlow → формы и дополнительные состояния.

Предлагаемые адреса внутри каждой локали:

- `/ru/` — главная;
- `/ru/diagnostics/` — диагностика;
- `/ru/coordination/` — координация;
- `/ru/simulator/` — симулятор с текущей последовательностью модулей;
- `/ru/foodflow/` — FoodFlow, если включён в согласованный объём.

Для kk/en — аналогичные пути. Модули симулятора могут иметь якоря, если это улучшит навигацию; отдельные маршруты не обязательны.

- Сохранить старые hash/query-входы через небольшой клиентский слой совместимости. Фрагмент URL сервер не видит, поэтому обычного серверного редиректа для `#simulator` недостаточно.
- Проверить прямой вход, обновление страницы и Back/Forward, а не только клики с главной.
- Разбить монолит на смысловые секции и вынести повторяемые данные из разметки.
- Для тяжёлых демо использовать разделение кода и загрузку по необходимости; не тащить все модули симулятора в бандл главной.
- Использовать встроенные возможности Svelte для анимаций; учитывать prefers-reduced-motion. Не переносить React motion как обязательную зависимость.
- Переиспользовать медиа; оптимизировать большие изображения и загрузку видео без потери качества. Видео не предзагружать целиком и не помещать в общий precache.
- Все модалки строить на Dialog. Форму — на готовых компонентах с labels, проверкой полей, sending/success/error и защитой от повторного нажатия.
- В локальных тестах подменять отправку заявок. Не отправлять тестовые персональные данные на реальную почту.
- До боевой отправки согласовать FormSubmit как внешний сервис, получателя и правила обработки данных. Если выбран собственный API, спланировать отдельный небольшой FastAPI-сервис; статическая сборка не выполняет серверные form actions.
- Недостающий PDF обозначить честно; не создавать фиктивное скачивание.

Результат: согласованные сценарии работают, а новая версия не регрессирует относительно текущей.

## 6. SEO, доступность, производительность и PWA

- Локализованные title/description, canonical, hreflang (`ru`, `kk`, `en`), Open Graph, sitemap и открытый robots.txt.
- Семантический H1, правильная иерархия заголовков; публичный контент доступен в собранном HTML без исполнения JS.
- WCAG 2.1 AA как цель: контраст, фокус, клавиатура, закрытие Dialog по Escape, возврат фокуса, labels, reduced motion.
- Все маршруты/локали перечислены для предрендеринга; настоящая 404 не заменяется главной для любого неизвестного URL.
- Измерить начальный JS, LCP/CLS и загрузку медиа на эталонном окружении. Уменьшение бандла подтвердить замером, а не обещанием от смены фреймворка.
- Отдельно решить необходимость offline/PWA. Не копировать старый sw.js вслепую. Если PWA остаётся — версионировать кеш, проверить обновление и исключить видео из precache.
- Для будущей замены приложения подготовить переход со старого service worker, чтобы посетители не оставались на закешированной React-версии.

## 7. Локальная приёмка

Обязательные проверки:

- `pnpm check`, lint, форматирование, Vitest, Playwright, production build проходят без ошибок.
- В браузере нет ошибок гидратации, необработанных исключений и отсутствующих ресурсов.
- Главная, все контуры, симулятор и согласованные демо работают на 390/768/1440 px без горизонтального скролла.
- Снимки до/после сравниваются; визуальное приближение оценивается человеком и при необходимости glm-5.3-flash, не только автоматическим diff.
- Языки переключаются на текущем маршруте; нет пропавших сообщений или обрезанного казахского/английского текста.
- Модалки, мобильное меню, видео и состояния формы проверены мышью и клавиатурой. Сеть формы замокана.
- Старые ссылки, прямые входы и Back/Forward работают в production preview.
- В статическом HTML присутствует нужный язык, текст и SEO-метаданные; robots.txt не закрывает сайт.
- Неиспользуемые React/Figma-артефакты не попадают в новую сборку.

После этого — демонстрация пользователю и подтверждение готовности. Сборка не равнозначна приёмке всего сайта.

## 8. Следующий этап — только после локальной приёмки

Деплой, доступ к GitHub и инфраструктура планируются отдельно. Не менять сейчас nginx, второй сайт, сертификаты и контейнеры сервера.
